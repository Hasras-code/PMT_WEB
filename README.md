# PMT Family university LMS

PMT_WEB is a university learning-management and cohort platform. It includes student registration and verification, cohort membership and role management, courses, resources, Kuppi recordings, announcements, complaints, public content, gallery, events, and cohort fund management.

This repository contains two independently buildable applications:

- A Go REST API at the repository root.
- A React, TypeScript, and Vite frontend under `frontend/`.

## Technology

- Go 1.26, Chi, pgx, PostgreSQL 17, golang-migrate, JWT, bcrypt, and structured logging
- React 19, TypeScript, Vite, Tailwind CSS, Axios, and Zustand
- Docker Compose for local PostgreSQL and Mailpit
- OpenAPI generated from the mounted API router

## Local setup

Requirements are Go 1.26.8 or newer, Node.js 22, npm, Docker Compose, and Python 3.

Start the database, mail service, migrations, and API:

```sh
make init
make db-up
make migrate-up
make run
```

`make init` creates a gitignored `.env` with a random signing secret and does not overwrite existing configuration.

Start the frontend in another terminal:

```sh
cd frontend
npm ci
npm run dev
```

Local services:

- Frontend: http://localhost:5173
- API: http://localhost:8080
- Swagger UI: http://localhost:8080/swagger/
- Mailpit: http://localhost:8025
- PostgreSQL: localhost:5432

Health endpoints require the separate HTTP Basic credentials configured through `AUTH_BASIC_USER` and `AUTH_BASIC_PASS`.

To run the API and migration command in containers:

```sh
make init
docker compose --profile app up --build -d
```

## Configuration

Copy `.env.example` for backend/local settings and `frontend/.env.example` for public frontend settings. Actual environment files are ignored.

The frontend's `VITE_API_URL` is the API origin, such as `http://localhost:8080`. API calls already include `/v1`.

Backend secrets, database credentials, mail credentials, and future R2 credentials must never be placed in frontend configuration. Values prefixed with `VITE_` are publicly visible in browser builds.

## Deployment overview

The intended production topology is:

- Go API: Google Cloud Run
- PostgreSQL: Supabase, using its shared Transaction Pooler for API traffic
- Frontend: Cloudflare Pages, using `frontend` as its root and `dist` as its output
- Object storage: Cloudflare R2 through a backend-only storage adapter, with local storage retained for development and controlled data migration

The root Dockerfile builds the API independently from the frontend. Cloudflare Pages builds entirely from `frontend/`. See [deployment and operations](docs/deployment.md) for environment ownership, migrations, rollback, and release checks.

## Collaboration

Keep `main` production-ready. Develop changes on focused branches, open pull requests, and require backend or frontend checks according to the files changed. Avoid mixing feature development with migration, deployment, or repository-maintenance changes unless they are inseparable.
